# 刑事摹拟画像 Skill 设计文档（最终交付版）

**部署目标**：Deepseek Harness / Agent Skills 开放格式
**文档性质**：开发规格说明书（可直接进入 Harness 实现）
**版本**：3.0（整合国内专业标准锚点、工程化骨架与竞品调研）
**核心验收口径**：见第 8 章。图像逆向分析与记忆正向构建分别验收；不承诺纯文本路径下任意场景的固定人脸相似度百分比。


## 0. 执行摘要与交付定位

本 Skill 是一个可安装到主流 Agent 的**刑事摹拟画像专业辅助工具**。它把法证面部形态学观察、中国公共安全行业标准的流程与编码锚点、认知访谈的非诱导提取、结构化画像规格（FPS）、跨模型提示词编译和质量评估，整合为两条可执行工作流：

- **工作流 1 · 图像逆向分析（Image-to-Description）** ：用户提供人脸图片，输出可按 GA 240.24 受控词汇对齐、可追溯、可交给画师或绘图模型的刑侦级结构化描述。
- **工作流 2 · 记忆正向构建（Memory-to-Portrait）** ：用户无参考图，通过非诱导认知访谈提取记忆，生成 FPS 与 AI 生图提示词。

两条工作流共用 FPS 作为唯一中间表示。竞品调研（第 2 章）表明：**Agent Skill 形态的通用人像 Prompt 生成器已存在，生成端的扩散模型管线已有可参考实现，但“刑事摹拟画像专业流程 + 非诱导访谈 + 可追溯 FPS”的交集尚属空白**——本 Skill 定位的正是这一空白。

**交付原则**：以初版的专业判断为纲（关系层优先、纯文本边界诚实、国内标准锚点锋利），以 Codex 文档的工程规格为目（FPS 数据模型、状态机、可评测），以竞品调研为佐证与组件来源（第 2 章）。三者不拼接，而是按“依据 → 调研 → 知识库 → 数据模型 → 工作流 → 编译 → 评测 → 实现 → 边界”的顺序重新组织。


## 1. 设计依据与专业标准锚点

### 1.1 三项来源的定位与适用边界

**（1）GA/T 601—2006《犯罪嫌疑人模拟像制作规则》——流程规范锚点。**

该标准规定制作犯罪嫌疑人模拟像的“要求、规程”，适用于制作犯罪嫌疑人模拟像，也适用于制作证人、受害人模拟像。它为本 Skill 提供的是**摹拟画像作为一项制作活动的流程合法性依据**：摹拟画像不是“画一张像”，而是有特定目的、特定适用对象和特定规程的制作行为。工作流 2 在流程定位上应与此标准对齐，输出服务于“模拟像”用途，而非普通肖像创作。**但 GA/T 601 是流程规则，不是面部特征词表**；不得从中衍生或声称衍生出“标准五官分类”。

**（2）GA 240.24—2003《刑事犯罪信息管理代码 第24部分：体貌特征分类和代码》——受控词汇与结构化编码锚点。**

该标准将面部解构为可独立编码的子单元，采用矩阵式分类，脸型分为十类、眼型分为八类，并涵盖眉、鼻、口、耳等子单元及特殊标记编码位。对本 Skill 而言，其核心价值不在于“提供一套人脸标准”，而在于**将面部描述转化为可校验、可比对的结构化代码串的方法论**。Skill 的受控词汇表（第 3.2 节）在中文术语选择和取值粒度上应优先与 GA 240.24 对齐，使输出具备与公安信息交换体系兼容的潜力。**须明确**：GA 240.24 是信息管理代码标准，其分类服务于信息交换与检索，不声称是对人脸“正确形态”的规范定义。

**（3）FISWG 面部形态分析特征清单——组件覆盖完整性框架。**

FISWG 的 *Facial Image Comparison Feature List for Morphological Analysis* 定义了 19 个面部组件及其特征和描述符，其范围声明明确写道：该指南**不定义比较过程本身**，只定义比较中使用的特征集；**不定义分类系统**来约束这些描述符应如何被表述。因此 FISWG 清单的价值是**组件和观察维度的完整性**，而非可直接套用的类型代码。Skill 以 FISWG 19 组件作为逐项复核的检查清单，受控类型取值则主要来自 GA 240.24 和刑侦实务术语。

**来源适用性矩阵**（Harness 实现时作为 `references/01-professional-sources.md` 核心内容）：

| 来源               | 类型                       | 可支持什么                             | 不可支持什么                         |
| ------------------ | -------------------------- | -------------------------------------- | ------------------------------------ |
| GA/T 601—2006      | 行业标准（流程规则）       | 摹拟画像的制作目的、适用对象、规程定位 | 面部特征分类、类型取值、特征词表     |
| GA 240.24—2003     | 行业标准（信息代码）       | 受控类型取值的中文术语、矩阵式编码逻辑 | 人脸形态的“正确性”规范、美学标准     |
| FISWG Feature List | 专业工作组指南（图像比较） | 19 组件覆盖清单、每组件观察维度        | 比较流程本身、分类系统、记忆访谈规程 |

### 1.2 认知访谈的指令序列与效果边界

认知访谈的原始版本包含四项记忆提取指令：**心理情境重现、报告一切、改变时间顺序、改变视角**。元分析证据显示认知访谈整体可提升目击者回忆准确率约 41%。但近期研究对“改变视角”指令提出重要限定：在四项指令中，除“改变视角”外其余指令均有助于促进准确信息回忆；而“改变视角”不仅未显著提升准确性，其单独效果存疑。

这一证据对访谈设计具有直接约束：**“改变视角/换位回忆”不得作为强制步骤使用，只能作为条件性可选项**——仅在用户对某一组件完全无法推进、且明确表示愿意尝试时，以柔和措辞提出，其结果必须标注为较低置信度（见 5.1 阶段 D）。


## 2. 竞品与可复用组件调研

### 2.1 调研结论

截至 2026 年 11 月，**未发现与本设计完全对齐的现成产品或开源项目**。但存在若干在单一能力上高度相关的项目，可作为技术参考或组件复用。核心结论：

1. **Agent Skill 形态的先例存在，但无刑事专业版**：huangserva/skill-prompt-generator 验证了“Skill + 人像 Prompt 生成”的产品形态，但其特征体系与访谈方法论未见刑事摹拟画像深度。
2. **生成端有可参考的学术实现**：Diff-FIT 证明了“文本特征描述 → 照片级面部合成像 → 局部编辑”的技术路径可行，其多管线编辑设计与本 Skill 的迭代修正协议同构。
3. **流水线有同构参考**：C72 框架的“自由文本 → 结构化 JSON → 确定性 Prompt → 图像”与本 Skill 的“访谈 → FPS → Prompt 编译”在工程思路上一致，但它是学术演示，非可安装 Skill，且访谈为表单/引导属性而非非诱导对话。
4. **实战案例印证了人机协同的正确边界**：“梅姨”第四版画像的流程——人工锁定核心刑侦特征 → AI 做质感渲染 → 人工二次复核剔除 AI 幻觉——与本 Skill“无依据编造率为 0%”“特殊标记前置强调”的红线完全一致。
5. **传统合成系统属于不同代际**：E-FIT、PRO-fit、EvoFIT 基于特征库视觉选择，研究显示命名率约 17%—19%；本 Skill 走的是“自然语言访谈 + 结构化描述 + AI 提示词”路径，方法论不同，不可直接对标。

> **调研时效声明**：以下竞品信息基于公开检索，具体实现细节、版本号与性能数据以 Harness 开发时自行核实为准；文档中的描述不作为对第三方项目能力的背书或精确断言。

### 2.2 Agent Skill 形态先例：huangserva/skill-prompt-generator

**是什么**：基于 Claude Skill 的 AI 人像 Prompt 生成系统，约 1k stars，核心能力包括 Prompt 生成、特征提取、自动学习和库扩展。

**可学习之处**：

- **产品形态验证**：它证明 Agent 生态中对“Skill 形式的人像提示词生成工具”存在真实需求，本 Skill 的封装形态有先例可循。
- **库扩展与版本管理**：其“特征库 + 自动学习 + 库扩展”的迭代机制，可作为本 Skill 后续扩充 `references/03-facial-feature-taxonomy.md` 和 `glossary` 的运营参考。

**与我们的差距**（即本 Skill 的差异化）：

- 未显现以 FISWG 组件清单或 GA 240.24 受控编码为骨架的专业特征体系；
- 未显现关系层编码（三庭比例、眼距/眼宽比、鼻翼/内眦间距等）与来源追溯机制；
- 无认知访谈——其输入是特征库组合，而非通过非诱导访谈从记忆中提取。

**吸收决策**：**不复用其代码或特征库**；在 `README.md` 中将其列为“Skill 形态先例”引用，并在差异化说明中明确本 Skill 在刑事专业深度与访谈方法论上的补位。

### 2.3 生成端参考：Diff-FIT（扩散模型面部合成像框架）

**是什么**：2026 年 3 月发表于 IEEE Access 的学术工作，源代码公开在 GitHub。用预训练扩散模型，从描述性特征衍生的文本提示生成照片级面部合成像，并支持三种后续编辑：全局图生图翻译、局部文本修复、基于拖拽的几何变换。用户研究显示其主观评价与识别率与当时最优系统相当，同时提供更大的变化灵活性。

**可学习之处**：

- **“生成 → 局部修复 → 几何调整”的多管线设计**，与本 Skill 第 8.4 节“迭代修正协议”的思路一致：首次生成后不是重写，而是**最小必要修改**。Harness 在实现迭代修正时，应参考“局部文本修复（inpainting）+ 几何调整”而非整段重写提示词。
- **文本特征描述到生成结果的路径可行性**，为本 Skill 的 Prompt 编译层提供了生成端的学术支撑。

**与我们的差距**：它是生成框架，不是 Agent Skill，也不包含访谈流程；解决的是“有了描述之后怎么画”，本 Skill 解决的是“如何系统性地产出可信的描述”。**生成端不是本 Skill 的核心价值所在**。

**吸收决策**：**不集成其代码**（避免引入扩散模型依赖，违背“模型无关、首版不绑定图像生成服务”的约束）；在第 7 章 Prompt 编译和第 8.4 节迭代修正协议中，**吸收其“最小必要修改 + 局部修复优先”的编辑策略**作为设计参考。

### 2.4 流水线参考：C72 框架（SCITEPRESS 2026）

**是什么**：将目击者的自由文本描述或引导式属性输入转换为结构化 JSON，再生成逼真人脸；使用 Gemini 进行属性解析和图像生成，包含确定性 Prompt 构建流程以保持年龄、肤色、发型、面部特征等属性在多次生成中一致，并设有伦理防护（同意验证、防止公众人物相似）。形态为 Streamlit 学术演示。

**可学习之处**：

- **“自由文本 → 结构化 JSON → 确定性 Prompt”流水线**与本 Skill 的“访谈 → FPS → Prompt 编译”在工程思路上同构，验证了结构化中间表示的必要性。
- **确定性 Prompt 构建以保持跨次生成一致性**，可直接吸收进本 Skill 第 7.1 节“身份锁定前置”与第 7.4 节“平台适配不改变特征事实”的规则。
- **伦理防护设计**（同意验证、防止公众人物相似）可作为本 Skill 第 10 章安全边界的补充参考：在记忆模式生成前增加“用户确认信息来源合法”的轻量提示。

**与我们的差距**：学术演示形态，非可安装 Skill；访谈环节为表单/引导属性，而非非诱导对话——这恰是本 Skill 明确要避免的（“不是让用户填一张五官问卷”）。

**吸收决策**：**吸收“自由文本 → 结构化 → 确定性 Prompt”的流水线思路**（本 Skill 已以 FPS 实现），**吸收伦理防护的轻量提示设计**；不引入其 Gemini 依赖。

### 2.5 平台参考：Decoders-AI 与 EricR401S

**Decoders-AI / stable-diffusion-forensic-identification-working**：基于 Stable Diffusion 的嫌疑人面部素描生成平台，架构包含 Prompt Generator LLM（从描述中提取面部特征并精炼）、Stable Diffusion 生成、Image-to-Image 精修器。

**EricR401S/gen_ai_hackathon**：面向执法部门的素描生成工具，声称“按警方素描标准设计，包含 19 个面部细节维度”，用户逐项填写描述，系统调用 DALL·E 生成图像。

**可学习之处**：

- Decoders-AI 的“Prompt Generator LLM 提取特征并精炼”环节，与本 Skill 的 Prompt 编译层功能重叠，可作为**特征提取→精炼→生成**三段式架构的工程参考。
- EricR401S 的“19 维度”清单可作为**组件覆盖完整性**的旁证（数字上与 FISWG 19 组件巧合，但其维度定义未经核实，不得直接采用）。

**与我们的差距**：两者均为 Web 平台，非 Skill；EricR401S 是**表单式输入**，恰是本 Skill 明确要避免的交互形态；Decoders-AI 未见访谈与非诱导规则。

**吸收决策**：**仅作架构旁证**，不集成代码；在 `references/03` 的组件清单注释中注明“FISWG 19 组件与业内常见的 19 维度清单在数量上一致，但本 Skill 采用 FISWG 原始定义”。

### 2.6 实战案例：梅姨第四版画像的人机协同边界

**是什么**：2026 年公开报道的实战案例（林宇辉）。流程为：人工手绘锁定核心刑侦特征（颅相、骨骼结构、经证人验证的五官）→ AI 大模型做质感渲染和彩色化 → 人工二次复核剔除 AI 幻觉（凭空捏造的疤痕、畸变五官）。

**可学习之处**（对本 Skill 的设计印证）：

- **AI 不应改动核心结构特征，只应做后置优化**——印证本 Skill“必须锁定/不得锁定”二分法（7.1）与“为美观自动修正原始比例”失败条件（8.5）。
- **AI 幻觉是刑事画像的真实风险**——印证本 Skill“无依据编造率为 0%”红线（8.2）与“特殊标记前置强调、逐项登记”（4.2 A5）的必要性。
- **人工二次复核不可省略**——印证本 Skill 的“复述确认”（5.1 阶段 E）与“迭代差异诊断”（8.4）机制。

**吸收决策**：**不吸收为流程步骤**（本 Skill 是 Agent 辅助工具，不替代人工复核）；但将“AI 不得改动核心结构、幻觉必须拦截”写入第 10 章边界声明与 8.5 失败条件，作为设计原则的实战背书。

### 2.7 传统合成系统：E-FIT / PRO-fit / EvoFIT 的定位差异

**是什么**：英国警方长期使用的计算机化面部合成系统，基于特征库视觉选择与组合。研究显示 E-FIT 命名率约 19%、PRO-fit 约 17%、传统素描约 9%。

**与我们的差距**：它们是**交互式视觉选择工具**，用户从库中挑选五官组合；本 Skill 走的是**自然语言非诱导访谈 + 结构化描述 + AI 提示词**路径，方法论属于不同代际。命名率数据不可直接迁移到本 Skill 的验收，因为输入形态、输出形态和评估场景均不同。

**吸收决策**：**不吸收其技术**；在 `references/06` 的访谈方法论注释中引用其命名率数据作为“传统方法基线”的背景说明，但明确声明本 Skill 的评估设计（第 8 章）独立于该数据。

## 3. 面部特征知识库：三层结构

### 3.1 组件层：必检清单（FISWG 19 组件为骨架）

以 FISWG 19 组件作为逐项复核的完整性保障：皮肤、头面部轮廓、面部构成（比例关系）、头发/发际线、额头、眉毛、眼睛、面颊、鼻子、耳朵、口部、下巴/下颌线、颈部、面部毛发、面部纹路、疤痕、面部标记、外观改变（妆容/修饰/穿孔/饰品）、其他。每个组件在 FPS 中**必须有明确状态**：已观察、用户回忆、未知、不可见、不适用或冲突待决。不允许“跳过且不标注”。

> 注：业内部分工具（如 EricR401S）也使用“19 维度”表述，但维度定义未经核实；本 Skill 采用 FISWG 原始定义，来源见 1.1。

### 3.2 类型层：受控词汇（优先对齐 GA 240.24）

每个组件下挂载有限类型取值。以可确认的 GA 240.24 分类粒度为例：脸型十类、眼型八类。类型层的功能是**为画像描述和提示词生成提供有明确解剖学/刑侦学含义的词汇**，防止“鼻子有点大”“眼睛挺好看”之类不可操作的表述。

**关键设计规则**：

- 类型取值是**描述工具**，不是人脸“应然标准”。目标人脸无法归入现有类型时，允许使用描述性自由文本，但须标注“未归类”，不得强行塞入最接近的类型。
- 类型取值携带来源标记：`ga240_24` / `operational` / `descriptive`。不得把 `operational` 取值伪装成标准取值。
- 低置信度的类型赋值不得在提示词中作为硬约束使用。

### 3.3 关系层：FPS 的一等公民

关系层是达到可辨认相似度的**真正瓶颈**，必须从“描述段落中的一句话”升级为 FPS 中的独立结构化字段（`spatial_relationships`），每一条关系记录携带与单项特征同等的 `source`、`confidence` 和 `evidence_reference`。

**应编码的内容**：

- 三庭比例关系：上庭（发际线—眉弓）、中庭（眉弓—鼻底）、下庭（鼻底—颏底）的相对高度关系，标注偏离方向和程度。
- 五眼关系：双眼内眦间距相对于单眼宽度的关系；眼外角至面侧缘的距离关系。
- 鼻—眼关系：鼻翼宽度与内眦间距的相对关系。
- 口—鼻/眼关系：口裂宽度相对于鼻翼宽度或瞳孔间距的关系。
- 耳—眉/鼻关系：耳廓上缘与眉弓、耳廓下缘与鼻底的水平对应关系。
- 颧—下颌关系：颧部宽度与下颌角宽度的相对关系。
- 中轴对齐：眼、鼻、口的中轴对齐或偏斜。

**必须内置的约束**（来自 FISWG 明确告诫）：FISWG 清单中的 “distance” 或 “approximate distance” **不意味着必须确定精确数值，而是指相对于整体脸宽/脸高的相对大小**。Skill 的关系层输出一律为**相对比例与偏离方向**，不得输出伪精确的绝对测量值。单张二维照片不能支持可靠的真实绝对尺寸推断；透视畸变和镜头距离导致的比例变化不得当作人体真实结构。

**三庭五眼的定位**：基准参考，不是规范。目标人脸偏离基准时，**记录偏离**，不得为使画像“更标准”而修正。


## 4. FPS：Facial Portrait Specification 数据模型

### 4.1 根对象

```json
{
  "schema_version": "3.0",
  "task_mode": "image_to_description | memory_to_portrait",
  "subject_reference": "user_supplied_image | user_memory",
  "image_conditions": {},
  "global_impression": {},
  "features": [],
  "spatial_relationships": [],
  "distinctive_features": [],
  "uncertainties": [],
  "conflicts": [],
  "prompt_constraints": {},
  "provenance": {},
  "quality_review": {}
}
```

### 4.2 单项特征记录

```json
{
  "feature_id": "eyes.left.upper_eyelid",
  "region": "eyes",
  "side": "left",
  "observation": "上眼睑褶皱可见，褶皱线位于睑缘上方约睑裂高度的 1/4 处",
  "normalized_descriptors": ["visible_upper_eyelid_crease"],
  "descriptor_source": "ga240_24 | operational | descriptive",
  "source": "image_observation | user_recall | user_correction | inference | conditional_prompt",
  "visibility": "clear | partial | obscured | not_visible | not_applicable",
  "confidence": 0.88,
  "importance": "high | medium | low",
  "stability": "relatively_stable | variable | temporary | unknown",
  "evidence_reference": "image_01 | interview_round_03",
  "notes": ""
}
```

**不可违反的规则**：

- `inference` 与 `conditional_prompt` 类型的记录**不得自动提升**为 `image_observation` 或 `user_recall`。
- `confidence` 是描述证据充分程度的内部标记，不是身份置信度，也不是统计校准概率。
- `stability` 区分静态结构与临时状态（表情、妆容、光照）。`temporary` 特征默认不进入提示词锁定清单，除非用户明确要求复现。

### 4.3 置信度等级与左右侧约定

| 等级 |  数值范围 | 含义                                   |
| ---- | --------: | -------------------------------------- |
| 高   | 0.80–1.00 | 信息清楚、直接可见，或用户明确确认     |
| 中   | 0.55–0.79 | 大致可判断，但存在角度、光照或记忆限制 |
| 低   | 0.01–0.54 | 模糊、含混或依赖推断                   |
| 未知 |      null | 无法判断，不应猜测                     |

左右统一采用**人物自身的左侧/右侧**，报告同时标注 `subject_left` 和 `subject_right`；无法判断镜像时标记 `orientation_uncertain`。


## 5. 工作流 1：图像逆向分析（Image-to-Description）

**触发**：用户提供一张或多张人脸图片。多视角（正面 + 侧面/45°）优先联合使用。

### 5.1 输入质量检查（不可跳过）

记录：图片编号、分辨率、视角、头部姿态、光照条件、清晰度、遮挡物、是否存在明显滤镜/修图/变形、是否为镜像或方向不确定、可分析范围。

**质量不足时**：输出明确的“不可判定组件”清单，在 FPS 中标记 `not_visible` 或 `obscured`，**不得用猜测填补**。这是硬红线。

### 5.2 分析步骤

**A1 · 图像条件记录**（见 5.1）。

**A2 · 整体视觉印象（先于局部）** ：脸部整体长宽感、头面部轮廓类别、视觉重心、五官分布疏密感、最具辨识价值的 3—5 个可见特征。不得将情绪或人格判断写入客观结构。

**A3 · 全局几何骨架**：按 3.3 的关系层框架先建立构型基线——三庭比例关系、五眼关系、整体长宽比（以颧宽或下颌角宽为基准）。**先定骨架，再填局部**。

**A4 · 逐组件复核**：按 19 组件清单逐项检查，记录形态、类型赋值（含来源标记）、左右差异、相对比例、可见性、置信度、稳定性。

**A5 · 特殊标记登记与前置强调**：独立列出高辨识离散标记：痣（位置、大小、颜色深浅）、瘢痕（位置、方向、长度）、色素异常、耳垂形态、发际线特殊形态。这些标记具有**超比例价值**，须在锚点摘要中前置，而非埋在组件描述末尾。

**A6 · 空间关系与冲突复核**：检查关系层与单项特征之间的逻辑冲突（如“脸型狭长”与“下颌角间距宽于颧间距”通常不兼容）。**冲突时回到图片重新核对，不得自动取平均或强行调和。** 无法解决时在 `conflicts` 中保留记录，提示词中该维度标注“存疑，建议中性处理”。

**A7 · 生成输出**：面向用户呈现三层（锚点摘要 ≤80 字 → 结构化特征表 → 画师自由描述段 200—300 字），底层为 FPS；同时编译画师 brief 与提示词（第 7 章）。


## 6. 工作流 2：记忆正向构建（Memory-to-Portrait）

**流程定位**：与 GA/T 601—2006 所规范的“模拟像制作”对齐——输出服务于辨认目的，而非艺术创作。若用户场景涉及真实案件或证人证言，须在访谈开始前声明：正式访谈应由合格调查人员或专业访谈人员负责；本 Skill 是辅助工具，不替代正式程序。

### 6.1 访谈状态机与反诱导硬规则

Harness 须追踪每个组件的提取状态：未触及 / 已自由报告 / 已结构化确认 / 冲突待决 / 用户明确不知。

**阶段 A · 情境激活与来源确认**。
先不追问五官。引导用户回到记忆场景：“你是在什么情况下看到这个人的？当时的光线、距离、他的朝向、你注意到的第一个特征是什么？”同时确认信息来源：真实记忆、参考资料，还是创作构思。输出**记忆质量元数据**（观察距离、光照、暴露时长、注意焦点），用于后续置信度加权。不得询问与画像无关的身份信息。

**阶段 B · 自由回忆（Report Everything）** 。
指令用户“不加筛选地说出所有你还记得的关于这张脸的信息，哪怕你觉得不重要、哪怕不专业”。Agent **只记录，不纠正，不追问术语，不提供选项**。“鼻子有点鹰钩”“眼睛下面好像有东西”“脸挺长的但又不是很瘦”，全部原样捕获。

**阶段 C · 结构化引导提取（非诱导式）** 。
按组件清单逐个推进，遵守**先开放、后受控**：

- 先问：“关于这个部位，你还记得什么？”
- 仅当用户主动表示难以描述时，才提供少量受控词汇作为**脚手架**，且须明确措辞：“这些只是描述词，不是选项；如果都不符合，我们可以留空。”
- **禁止**二选一暗示性问题（“眼睛是不是很大？”“鼻子是不是高挺的？”）。
- 每个特征记录为三元组：**用户原话 → 映射到的受控类型（如有）→ 置信度**。三者不可合并，不得把 Agent 的映射表述当作“用户确认过的内容”。

**阶段 D · 条件性视角/顺序变换（非强制）** 。
基于 1.2 节证据，“改变视角”不得作为标准步骤强制执行。仅当用户对某一组件完全无法推进且明确表示愿意尝试时，使用柔和的条件性提示：“如果从侧面看，你觉得鼻子和下巴的关系可能会是什么样？”或倒序提示：“先别想眼睛，从下巴往上想。”此阶段产生的特征**置信度不得高于“低”**，来源标记为 `conditional_prompt`。

**阶段 E · 复述确认与冲突暴露**。
将汇总特征以简短摘要回呈，措辞必须明确区分“整理”与“确认”：“这是我从你的回答中整理的内容，**哪些地方是我表达得不准确？哪些是你没有说过的？** ”用户前后冲突时，温和指出“前面记录的是 A，刚才提到的是 B”，询问是补充、修正还是两个场景下的不同；**保留两条记录及其时间顺序，不得自动取平均或替用户裁决**。

**阶段 F · FPS 生成**。
仅在用户确认摘要后生成 FPS。未知字段保持 `null` 或 `not_visible`，不得为“填满”而补写。

### 6.2 禁止的提问方式（硬红线）

- “他的眼睛是不是很大？”（二选一暗示）
- “鼻子是不是高挺的？”（预设答案）
- “他看起来是不是很凶？”（人格推断）
- “你觉得他像不像某个名人？”（外部锚点污染）
- 把 Agent 生成的示例描述当作“你刚才说的是这个意思吧？”的回读。


## 7. Prompt 编译系统

### 7.1 编译原则

**原则一：身份锁定前置**。提示词最前端放置紧凑的身份定义块，锁定脸型、颌线、鼻型、眼型/眼距、唇形、显著不对称和用户确认的特殊标记。SD 类模型对序列前部 token 权重更高；身份描述必须位于场景、光影、风格之前。

**原则二：构型关系优先于孤立特征形容词**。关系性表述（“内眦间距略宽于单眼宽”“中庭略长于上庭”）优先于“眼睛大”“脸长”之类的孤立描述。

**原则三：确定性 Prompt 构建**（吸收 C72 框架思路）。同一 FPS 在多次生成、不同平台适配时，身份锁定块的语义内容**逐字不变**；变化只发生在参数语法与组织方式。

**原则四：锁定/不锁定二分**。

| 必须锁定（高重要性 + 高置信度 + 稳定） | 不得锁定                                       |
| -------------------------------------- | ---------------------------------------------- |
| 脸型宽窄与下颌轮廓                     | 未知或低置信度特征                             |
| 眼距、眼裂形状、眼睑结构               | 图片中不可见的耳部/头顶结构                    |
| 鼻梁、鼻尖、鼻翼形态                   | 用户未提供的族群、人格、健康标签               |
| 嘴宽、唇形、嘴角                       | 绝对尺寸/伪精确测量值                          |
| 显著左右不对称                         | `temporary` 稳定性特征（除非用户明确要求复现） |
| 用户确认的可见特殊标记                 | `conditional_prompt` 来源的低置信度特征        |

### 7.2 通用 Prompt 模板

```text
[IDENTITY LOCK — highest priority]
Face structure: [脸型 + 三庭比例关系 + 五眼关系 + 整体长宽比].
Jaw and chin: [下颌宽度 + 下颌角转折 + 下巴形态与突出度].
Nose: [鼻根高度 + 鼻梁曲度 + 鼻尖形态 + 鼻翼宽度相对于内眦间距].
Eyes and brows: [眼裂形状 + 睑型 + 眼角倾斜 + 内眦间距 + 眉形/密度/眉峰位置].
Mouth: [口裂宽度相对于鼻翼/瞳孔间距 + 唇厚薄 + 嘴角倾向 + 人中].
Distinctive: [特殊标记的精确位置、形态、相对大小].

[COMPOSITION AND LIGHTING]
Straight-on frontal portrait, neutral expression, even diffused lighting,
no shadow distortion on facial contours, neutral background.

[STYLE]
[photorealistic / pencil sketch / forensic composite style].

[NEGATIVE CONSTRAINTS]
No beautification, no facial slimming, no skin smoothing that erases
texture or marks, no idealized proportion normalization, no invented
scars/moles, no altered eye spacing, no altered nose shape, no altered
jawline, no expression exaggeration, no dramatic lighting.
```

**Negative Prompt 的通用优先原则**：首版不维护各平台复杂语法，先输出通用 Prompt + Negative Prompt。平台适配器（Midjourney / SDXL / FLUX / DALL·E）只改变参数语法和组织方式，**不得改变 FPS 中的面部特征事实**。

### 7.3 参考图优先策略（对 90% 目标的诚实处理）

当前主流图像生成工具中，**参考图/身份锁定是保持面部一致性的主导路径**：PuLID、InstantID、PhotoMaker、IP-Adapter-FaceID、MJ `--cref` 等方法的身份保持能力显著高于纯文本提示词路径；纯提示词工程在身份保持上的稳定性存在明显上限。

保真度策略分层：

- **若用户有任何可用参考图**（目标本人照片，或特征组合相似的脸部图片），**优先引导参考图 + 提示词联合控制**。Prompt 约束结构、画风和变化范围；参考图提供文本难以完整编码的高维视觉细节。
- **若用户仅有文本/记忆输入**，Prompt 优先保证构型关系，并明确告知：纯文本路径的相似度**不保证达到某一固定百分比**；建议通过迭代修正协议逐步逼近（8.4）。
- **不得声称“本 Skill 仅凭文字提示词即可稳定达到 90% 真实人脸复现率”** 。这不是谦辞，是基于当前工具能力的专业判断。


## 8. 质量评估与验收标准

### 8.1 两类工作流分别验收

图像逆向分析与记忆正向构建的输入条件本质不同，**不得使用同一套分数直接比较，不得对记忆模式承诺身份相似度百分比**。

### 8.2 图像逆向分析：开发期指标 + 验收期指标并置

**开发期指标**（用于 Harness 迭代定位问题）：

| 指标                                      |   目标 |
| ----------------------------------------- | -----: |
| 19 组件覆盖率（已观察/已标记未知/不适用） |   ≥95% |
| 可见且有区分度组件的类型命中率            |   ≥90% |
| 关系层（三庭/五眼/鼻—眼/口—鼻）准确率     |   ≥90% |
| 无依据编造率                              | **0%** |
| 内部冲突未解决率（未标注即输出）          | **0%** |

**验收期指标**（四维框架）：

| 维度           | 含义                               |             首版目标 |
| -------------- | ---------------------------------- | -------------------: |
| 特征保真度     | 高重要性特征在重绘图中是否保留     |      ≥90/100（盲评） |
| 整体相似感     | 独立评审者的整体相似评分           | 作为实验目标逐轮提升 |
| 可辨特征保留率 | 显著、稳定、可见的个体特征是否保留 |                 ≥90% |
| 提示词遵循度   | 视角/表情/光照/构图是否符合约束    |                 ≥90% |

### 8.3 记忆正向构建的验收

**不对真实人物身份相似度作 90% 承诺**。评估设计：参与者先观察测试人脸 → 经过间隔后不再显示参考图 → 使用 Skill 访谈 → 生成 FPS → 独立绘图 → 盲评匹配。对照组包括普通自由描述和结构化五官问卷，以检验非诱导访谈是否比普通描述产生更准确的特征记录。

### 8.4 迭代修正协议（吸收 Diff-FIT 编辑策略）

首次生成后，Skill 提供**差异诊断清单**，对照 FPS 逐项检查：脸型是否匹配、内眦间距是否过宽/过窄、鼻梁起点高度是否正确、下颌角宽度是否保留、特殊标记是否出现。

修正方式遵循**最小必要修改 + 局部修复优先**：

- 优先调整身份锁定块中的单个维度（如仅修改“内眦间距”表述），而非整段重写；
- 若绘图工具支持局部修复（inpainting）或几何调整，建议用户在该区域做局部修正，而非全图重生成；
- 每次修正后重新执行差异诊断，记录修改前后的提示词版本，便于回溯。

### 8.5 硬性失败条件（任一项出现即视为严重缺陷）

- 编造参考图中不可见或用户未回忆的特征；
- 将 `inference` / `conditional_prompt` / 低置信度记录写成事实；
- 访谈中出现二选一暗示或预设答案；
- 高重要性特征在 Prompt 编译中丢失；
- 为美观自动修正原始面部比例或“标准化”不对称；
- 输出身份识别、嫌疑人认定、人格/族群/健康推断；
- 以“90% 相似”作无实验设计支持的保证；
- 把 FISWG 清单描述成摹拟画像完整流程标准，或把 GA 240.24 分类描述成人脸“正确形态”标准。


## 9. Harness 实现要点

### 9.1 目录结构


### 9.2 SKILL.md 职责边界

`SKILL.md` 是入口和路由器，不是知识百科。须包含：Skill 名称与触发条件、两种模式路由、安全边界（第 10 章）、FPS 输出要求、质量检查要求、知识文件按需加载指引。Agent 仅在需要特定主题时读取对应 reference。

### 9.3 来源元数据规范

每条知识记录至少包含：`id`、`title`、`source_type`（`official_standard` / `peer_reviewed_research` / `operational`）、`publisher`、`version`、`published_at`、`source_url`、`applicability`、`limitations`、`summary`。不得把二手博客或模型生成内容标记为权威标准。

### 9.4 运行约束

- 首版不主动上传用户图片至第三方服务；外部工具调用由宿主 Agent 能力和用户授权决定。
- 不在 Skill 内保存用户图片或人脸特征数据；不建立人脸向量库或身份检索功能。
- 不要求用户提供真实姓名、证件号或案件编号。
- 不绑定特定 LLM 或图像生成平台。
- 记忆模式生成前，轻量提示用户确认信息来源合法（吸收 C72 伦理防护思路）。


## 10. 专业边界与安全

### 10.1 四个概念的严格区分

| 概念                                        | 本 Skill 是否支持                            |
| ------------------------------------------- | -------------------------------------------- |
| 面部形态描述                                | **支持**（工作流 1 的核心）                  |
| 刑事摹拟画像（facial composite）            | **支持辅助流程**（工作流 2，不替代正式程序） |
| 法证面部图像比较（facial image comparison） | **不提供**（需受训人员按专门标准执行）       |
| 人脸识别（face recognition）                | **严禁**                                     |

### 10.2 绝对禁止的输出

- 根据人脸图像识别、确认、推断或搜索人物身份；
- 声称某人是嫌疑人、犯罪者或与某案件有关；
- 输出身份匹配结论、身份置信度或生物特征模板；
- 从脸部推断族群、宗教、性取向、健康状况、犯罪倾向、人格或其他敏感属性；
- 将图片模式的输出称为“法证身份鉴定结论”；
- 将记忆模式生成的画像包装成“已验证的嫌疑人肖像”。

### 10.3 人机协同边界的实战背书

“梅姨”第四版画像的实战流程印证：**AI 不应改动核心结构特征，只应做后置优化；AI 幻觉（凭空捏造的疤痕、畸变五官）是刑事画像的真实风险，必须由人工复核拦截。** 本 Skill 据此确立：核心结构特征只由 FPS 的高置信度记录锁定，AI 生成结果不得被当作结构事实；特殊标记必须逐项登记、前置强调；任何生成结果在用于辨认目的前，须经用户或专业人员复核。

### 10.4 90% 目标的最终措辞

“相似度不低于 90%”是**产品在限定测试条件和限定验收方法下的工程目标**，不是对任意用户、任意图片、任意绘图模型的普遍能力承诺。图像逆向分析可在固定测试集和固定绘图配置下以盲评 90/100 为目标；记忆正向构建**不承诺**真实身份相似度百分比。高保真场景必须允许并建议使用参考图联合控制。


## 11. 开发任务拆分（供 Deepseek Harness 执行）

### Phase 1 · Skill 骨架
交付：标准目录、`SKILL.md`、`README.md`、元数据、安全边界、双模式路由。
验收：可被目标 Agent 正确发现；能根据请求选择正确模式；不触发身份识别等非目标功能。

### Phase 2 · 专业知识库
交付：19 组件分类、解剖与形态术语、关系层规范、图像观察规程、认知访谈规程（含非诱导规则）、中英术语表、来源元数据。
验收：19 组件覆盖完整；受控词汇来源标记正确（`ga240_24` / `operational` / `descriptive`）；官方资料与自编操作规范明确区分；无伪标准。

### Phase 3 · FPS 数据模型
交付：JSON Schema、特征记录结构、置信度/可见性/来源枚举、冲突记录、校验脚本。
验收：JSON 可通过 Schema 验证；未知字段可为空；推断不得标成直接观察；左右侧定义一致。

### Phase 4 · 双工作流
交付：Image-to-Description、Memory-to-Portrait、报告模板、访谈状态管理、用户确认与纠错机制。
验收：两模式独立工作；访谈非诱导；图片分析不编造不可见特征；输出统一为 FPS。

### Phase 5 · Prompt 编译与质量控制
交付：通用 Prompt 模板、Negative Prompt、画师 brief、锁定/不锁定二分规则、迭代修正协议、评测说明。
验收：高重要性特征不丢失；未知特征不补写；支持纯文本与参考图两种建议；不宣称未经验证的相似度。

### Phase 6 · 竞品引用与交付
交付：README 中竞品差异化说明（第 2 章内容摘要）、安装说明、测试案例、示例输入输出、发布包。
验收：至少在一个目标 Agent 中完成端到端测试；文件结构无多余依赖；文档可独立理解；竞品引用无背书误读。


## 12. 关键设计决策摘要

1. **FPS 是唯一中间表示**。两条工作流都汇入 FPS，再从 FPS 编译为报告和提示词。
2. **关系层是一等字段**，不是特征数组的附属品；输出相对比例与偏离方向，不输出伪精确测量值。
3. **GA 240.24 提供受控词汇与编码逻辑，GA/T 601 提供流程合法性锚点，FISWG 提供组件覆盖清单**；三者适用范围在来源矩阵中硬性区分。
4. **认知访谈的“换位/改变视角”降级为条件性可选步骤**；基于当前证据，其单独使用可能不提升准确性。
5. **非诱导是硬规则**：先开放后受控，禁止二选一暗示，Agent 映射不得冒充用户确认，冲突保留不取平均。
6. **纯文本路径的相似度边界必须诚实声明**；参考图联合控制是高保真场景的首选路径。
7. **无依据编造率为 0% 是红线**，不是“尽量做到”。
8. **竞品调研的价值在于验证与差异化**，不在于代码复用：Skill 形态有先例（huangserva）、生成端有参考（Diff-FIT）、流水线有同构（C72）、实战边界有印证（梅姨案例），但“专业标准锚点 + 非诱导访谈 + 可追溯 FPS”的交集仍是空白，本 Skill 定位于此。

**一句话定位**：一个以中国公共安全行业标准（GA/T 601 流程规范、GA 240.24 受控编码）为专业锚点、以 FISWG 组件清单为完整性骨架、以 FPS 为可追溯中间表示、以非诱导认知访谈为记忆提取引擎、以跨模型提示词编译为输出的**专业画像辅助 Agent Skill**——它不识别身份，不替代法证程序，不承诺无条件的百分比相似度；它的社会价值在于让每一次基于记忆的画像辅助都更少诱导、更可追溯、更少编造，从而让辨认更接近真实。
